# Ambassador Club Platform — Technical Document

## 1. Overview

A web-based platform for managing an Ambassador Club program. Ambassadors apply, get approved by an admin, complete activities for points, interact via chat, and redeem points (alone or combined with money) for merchandise and vouchers.

The system consists of two dashboards sharing a single backend:

- **User Dashboard** — for approved ambassadors
- **Admin Dashboard** — for the single platform admin

## 4. Database Schema

All tables live in the `public` schema. Supabase Auth manages `auth.users` separately; we link via `user_id UUID REFERENCES auth.users(id)`.

### Naming convention

All tables, views, and storage buckets owned by the Ambassador module are prefixed with `amb_`. The same Supabase instance is shared by the public Prime Engage site (`primeengage` repo) and this Ambassador platform repo — the prefix gives us a clean, non-colliding module boundary. Both repos use these prefixed names as the source of truth.

Columns, Edge Function names, and RLS policy names are **not** prefixed — only top-level database objects (tables, views, buckets).

### 4.1 `amb_profiles`
One row per applicant, ambassador, and admin. Pending applications live here before an `auth.users` row exists — on approval, an Edge Function creates the auth user and links it via `auth_user_id`.

| Column | Type | Notes |
|---|---|---|
| `id` | uuid (PK) | generated by us (`gen_random_uuid()`) |
| `auth_user_id` | uuid (FK → `auth.users.id`, nullable) | set on approval; null while `status='pending'` |
| `role` | text | `'admin' \| 'ambassador'` (default `'ambassador'`) |
| `status` | text | `'pending' \| 'approved' \| 'rejected' \| 'suspended'` (default `'pending'`) |
| `first_name` | text | |
| `last_name` | text | |
| `email` | text (UNIQUE) | dedup applications; lowercased at write-time |
| `phone` | text | E.164-ish, stored as entered and normalized |
| `college` | text | |
| `city` | text | |
| `student_id_url` | text (nullable) | storage path in `amb_applications` bucket |
| `avatar_url` | text (nullable) | post-approval |
| `application_data` | jsonb (default `'{}'`) | free-form application payload — see shape below |

| `rejected_at` | timestamptz (nullable) | set by rejection flow |

**`application_data` jsonb shape (v1):**

```jsonc
{
  "referral_code": "string | null",
  "why_join": "string",             // long text
  "stand_out": "string",            // long text
  "fest_involvement": "string",     // one of 5 fixed options — see lib/ambassador/types.ts

```

The canonical shape + option lists live in `lib/ambassador/types.ts` (Zod schema). Form UI, API route, and admin repo all import from there — never hard-code options.

## 5. Authentication & Authorization

### 5.1 Auth
- Supabase Auth, email + password only.
- Admin account is seeded manually (one row in `amb_profiles` with `role='admin'`).
- Ambassador accounts are created **only** by the admin's approval action (see flow below). No public signup into the dashboard.
- Public application form writes to a `pending` profile row (or an `amb_applications` staging table — see note below) without creating an auth user.

> **Implementation note:** We write applications directly into `amb_profiles` with `status='pending'` and `auth_user_id=NULL`. The `id` is a generated uuid owned by us (never changes). On approval, the Edge Function calls `supabase.auth.admin.createUser(...)`, then `UPDATE amb_profiles SET auth_user_id = <new uid>, status = 'approved', approved_at = NOW() WHERE id = $1`. `id` stays stable across the lifecycle so downstream FKs (future `amb_submissions.user_id`, etc.) can point to `amb_profiles.id` directly.

### 5.2 Authorization via RLS
Row-Level Security is enabled on every table. Sample policies:

- `amb_profiles`: a user can read/update their own row; admin can read/update any row.
- `amb_activities`: all approved ambassadors can SELECT active activities; only admin can INSERT/UPDATE.
- `amb_submissions`: ambassador can INSERT/SELECT their own rows (and only if the activity deadline hasn't passed, enforced via trigger); admin can SELECT/UPDATE all.
- `amb_chat_messages`: user can SELECT rows where they are sender or receiver; INSERT allowed if sender_id = auth.uid() and (sender or receiver is admin).
- `amb_products`: all authenticated users SELECT; admin only for writes.
- `amb_orders`, `amb_points_ledger`: user sees own; admin sees all. Writes go through Edge Functions only (no direct insert from client).

### 5.3 Middleware
Next.js middleware (`middleware.ts`) reads the Supabase session cookie, fetches the cached role, and:
- redirects unauthenticated users away from `/dashboard/*` and `/admin/*`
- redirects non-admins away from `/admin/*`
- redirects admins away from `/dashboard/*` (optional — they use admin panel)

## 6. Core Feature Modules

### 6.1 Ambassador Onboarding

```
Applicant fills form  ──▶  row inserted in amb_profiles (status='pending')
                           ──▶  confirmation email sent (Resend)
                           ──▶  admin sees in "Applications" tab

Admin clicks "Approve"
    ──▶  Edge Function: approve-application
         1. Generate random password
         2. supabase.auth.admin.createUser({ email, password })
         3. Link auth user id to the profile row
         4. Set status='approved'
         5. Send email via Resend with credentials + login URL
    ──▶  Ambassador receives email, logs in
```

Edge Function is required here because creating auth users needs the service-role key, which must never touch the client.

### 6.2 Activities

**Admin side:**
- Form to create activity: title, description, points, submission deadline, optional cover image.
- List view of all activities with submission counts.
- Click into an activity to view all ambassador submissions.

**Ambassador side:**
- List of all active activities with status: "Open" / "Closed" / "Submitted".
- Click → activity detail → upload form (multi-file + optional text).
- Submission locks immediately on save; no edit/resubmit.
- After admin awards points, status becomes "Awarded: X points" — visible in their dashboard.

**Deadline enforcement:** Postgres trigger on `amb_submissions` INSERT rejects rows where `NOW() > activity.submission_deadline`. Belt-and-suspenders with frontend validation.

### 6.3 Point Awarding

- Admin opens a submission, sees uploaded files + text.
- Enters award amount (can be less than the activity's default — admin discretion) and clicks "Award".
- Edge Function `award-submission`:
  1. Updates `amb_submissions.status='awarded'`, sets `awarded_points`, `reviewed_by`, `reviewed_at`.
  2. Inserts into `amb_points_ledger` with `delta = awarded_points`, `reason='submission_awarded'`.
  3. (Optional) Sends email to ambassador.

Awarding is one-shot per submission — the button disables after first award.

### 6.4 Chat

- Uses Supabase Realtime subscriptions on `amb_chat_messages`.
- Ambassador sees one chat thread (with admin).
- Admin sees a list of all ambassadors as threads, unread count per thread.
- On message receive, update `read_at` when thread is open.

Near-real-time is achieved via Postgres logical replication; no custom WebSocket server needed.

### 6.5 Events & Gallery

Both are simple admin-authored content surfaces:
- Admin posts events (title, body, cover image) and gallery images (file + caption).
- User dashboard lists them in reverse chronological order.
- No interactions, no comments, no RSVP.

### 6.6 Analytics (User Dashboard)

Small component showing:
- Current points balance (from `amb_v_user_balances`)
- Top 3 overall ambassadors by total earned points (from `amb_v_leaderboard`)
- Total points earned to date
- Total activities completed

### 6.7 Rewards Store

- Grid of products filterable by type (merch / voucher) and by affordability.
- Each product shows `points_cost` and `inr_cost`.
- Checkout flow:
  1. User clicks "Redeem".
  2. Frontend computes required points and required INR.
  3. If `inr_cost > 0`: initiate payment gateway flow (Phase 2).
  4. Edge Function `create-order`:
     - Verifies user has enough points.
     - Inserts `amb_orders` row with `payment_status='pending'` or `'not_required'`.
     - If payment needed, returns gateway order payload.
  5. Payment webhook (`payment-webhook` Edge Function) marks `payment_status='paid'` and inserts `amb_points_ledger` row with `delta = -points_used`.
  6. Admin fulfills manually (voucher code via email, merch shipping) and marks `fulfillment_status='fulfilled'`.

**Note on vouchers:** For v1, vouchers are "just a label" — admin delivers the code offline (e.g., via chat or email). A future phase will add auto-generated codes stored in a `voucher_codes` table and issued on order fulfillment.

### 6.8 Admin: Product & Rate Management

- CRUD on `amb_products` table.
- Edit global `points_to_inr_rate` in `amb_settings`. This rate is used for display and for converting hybrid pricing suggestions (not enforced on individual products, since each product has its own `points_cost` and `inr_cost`).

## 7. File Storage Strategy

Supabase Storage buckets:

| Bucket | Visibility | Contents |
|---|---|---|
| `amb_applications` | private | Student ID cards + any other application-time uploads. RLS: owner (auth_user_id after approval) + admin. During `pending` state, writes go through service role only. |
| `amb_submissions` | private | Activity submission files — RLS: owner + admin |
| `amb_activities` | public | Activity cover images (admin-uploaded) |
| `amb_gallery` | public | Gallery images |
| `amb_events` | public | Event cover images |
| `amb_products` | public | Product images |
| `amb_avatars` | public | Ambassador profile pics |

File size caps (enforced both client-side and server-side):
- **Student ID Card** (`amb_applications`): ≤ 5 MB, MIME whitelist `image/jpeg`, `image/png`, `image/webp`, `application/pdf`.
- Images (general): ≤ 5 MB.
- Videos: ≤ 50 MB.
- Docs: ≤ 10 MB.

Path conventions:
- `amb_applications/<yyyy-mm>/<profile_id>/<uuid>.<ext>` — application uploads scoped by month and profile id.
- `amb_submissions/<user_id>/<submission_id>/<filename>` — activity submissions.
- `<bucket>/<yyyy-mm>/<uuid>-<filename>` — admin content (gallery, events, products).

## 9. Payment Integration (Phase 2)

**Recommended: Razorpay** (cleaner DX for INR + hybrid flows; widely used in India). HDFC SmartGateway works too but integration is heavier.

Flow:
1. Frontend calls Edge Function `create-payment-order` with `product_id`.
2. Function validates points balance + computes INR due + creates Razorpay order + stores internal `amb_orders` row with `payment_status='pending'`.
3. Frontend opens Razorpay Checkout with returned `order_id`.
4. Razorpay posts to webhook → `payment-webhook` Edge Function verifies signature, updates order, debits points via ledger.
5. User sees "Order placed, awaiting fulfillment".

Keys stored as Supabase secrets, never exposed to client.

## 10. Security Checklist

- RLS enabled on **every** public table before go-live.
- Service-role key used only inside Edge Functions.
- All point-affecting writes (awarding, redemption) go through Edge Functions, not direct client inserts — prevents client-side tampering.
- File uploads validated by mime type + size both client-side and via Storage policies.
- Payment webhook signature verification mandatory.
- Admin account password rotated on first login; 2FA can be added in Phase 2.
- Rate-limit the public application form (Edge Function with IP-based throttle or Cloudflare Turnstile captcha) to prevent spam.
- CORS configured on Edge Functions to allow only the Vercel domain.
